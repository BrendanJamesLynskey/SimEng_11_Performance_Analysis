Measure Before You Optimise

A simulator that takes a minute gets run a hundred times a day; one that takes an hour gets run once, and its users start guessing instead. So simulator speed matters, and the first rule of making it faster is the one LLM Inference Simulators 08 calls step zero: profile first. Intuition about where time goes is wrong often enough that it is not worth acting on.

This deck applies the standard tools to the simulators in this series, on one desktop machine (an Intel i7-3770 with 8 logical CPUs, with a desktop session running), and reports what they found, including two things that were not expected:

  • The Rust port of Disaggregated_Inference_Sim spends 45% of its instructions sorting, in its metrics code, not in its simulation engine.
  • On this machine, a single-run timing gate with a 5% margin raises a false alarm on unchanged code 23% of the time.

Every number comes from snippets/t11/run_t11.py and profile_first.py, recorded in RESULTS.md.

02

Two Methods: USE for Resources, Profile First for Code

  • The USE method (Brendan Gregg) checks every resource (CPUs, memory, disks, network, locks) for Utilisation, Saturation (work queued because the resource is busy) and Errors. It finds system bottlenecks quickly, because it is a checklist rather than a guess.
  • The profile-first loop finds code bottlenecks. Its last step is the one that is skipped most often: check that the answers did not change. For a simulator, a faster wrong answer is a regression.
  • Profile the workload users actually run. A micro-benchmark of the event queue says nothing about a run dominated by metrics.

USE in Practice: a Parallel Sweep

Rust_DES_Kernel's disagg-rs --sweep runs one simulation per arrival rate in parallel with rayon. Here are eight rates of 4,000 requests each, under /usr/bin/time -v, on one thread and on eight:

ThreadsWall timeCPUUtilisation of 8 CPUsMax RSSVoluntary switchesInvoluntary switches
10.56 s99%12.4%36.3 MB320

Source: snippets/RESULTS.md in _simeng_build

  • Utilisation: eight threads kept 79.5% of the 8 logical CPUs busy and ran 2.8× faster, not 8×. The i7-3770 has 4 cores with 2 hardware threads each, so 8 threads share 4 sets of execution units. The desktop was also running.
  • Saturation: involuntary context switches rose from 20 to 214. Threads were pre-empted because there were more runnable threads than free CPUs.
  • Memory: peak resident memory grew 7.4×, because each simulation holds its own state. On a 15 GB machine, memory is the resource to watch for wide sweeps.
  • Errors: none here. In CI, out-of-memory kills and timeouts are the errors to look for.
04

Linux perf, and When You Cannot Use It

perf is the Linux profiler. perf stat counts hardware events (cycles, instructions, cache and branch misses, from which instructions per cycle follows); perf record samples call stacks for a profile; perf report and perf annotate show where the samples landed, down to the instruction. The perf wiki covers it in depth.

Command (not run here)Answers
perf stat -e cycles,instructions,cache-misses,branch-misses -- ./simIs it compute-, memory- or branch-bound? (instructions per cycle, misses per thousand instructions)
perf record -g -- ./sim then perf reportWhich functions, on which call paths, take the samples?
perf record -g then perf script into a flame-graph toolThe same profile, drawn as a flame graph
What happened on this machine
kernel.perf_event_paranoid is 4; perf stat -e cycles,instructions -- true exits with status 1: "Consider adjusting /proc/sys/kernel/perf_event_paranoid setting to open"

A setting of 4 (Ubuntu's default) denies performance events to unprivileged users, so none of the commands above could run. An administrator can lower it (see the kernel's perf security guide), which was not done here. The rest of this deck uses tools that need no privileges: py-spy, which reads a Python process's memory to sample its stacks, and cachegrind, which runs the program on a simulated CPU and counts every instruction.

05

Sampling Profilers and Flame Graphs

A sampling profiler interrupts the program at a fixed rate (here 500 times a second) and records the call stack. Functions that take more time appear in more samples. The overhead is small and the program does not need changing. The price is statistical noise for anything that takes only a few samples.

A flame graph merges identical stack prefixes. The width of a frame is the share of samples in which it was on the stack (its total time). The top edge of each tower is where the time is actually spent (self time). The x-axis is not time, so a wide frame is a hot spot, not a long phase.

Counting Instructions With Cachegrind

Cachegrind runs a program on a simulated CPU and counts every instruction, with a simple model of the caches. It is 20–100× slower than native, but deterministic: the same run gives the same count, so small changes can be compared without timing noise. Here are the same 500-request simulation in Rust and in Python:

ImplementationInstructionsInstructions per requestI1 miss rateD1 miss rateLL miss rate
Rust (disagg-rs)59,162,943118,3250.01%3.2%0.1%
Python (disagg-sim, SimPy)1,394,927,0762,789,8540.78%3.4%0.0%

Source: snippets/RESULTS.md in _simeng_build

  • Start-up, measured separately: Python with the simulator's imports 286,627,513 instructions; a one-request Rust run 847,816. Net of start-up: Python 2,216,599 and Rust 116,630 instructions per request, 19x (gross: 24x).
  • Neither run is cache-bound: the working set fits, and both miss the last-level cache on 0.1% or fewer of references. The difference is purely instructions, interpreter work against compiled code.

Closing the Loop: Sort Once

Hypothesis: _dist calls percentile for p50, p90 and p99, and each call sorts the whole list again. For inter-token latencies that list has 763,474 values. Change: sort once and take all three percentiles from the sorted list. Check: summarise must return exactly the same answers.

snippets/t11/profile_first.py source
def _dist_sort_once(xs: list[float]) -> dict:
    s = sorted(xs)
    return {"mean": metrics.fmean(xs) if xs else math.nan, "p50": _percentile_sorted(s, 50),
            "p90": _percentile_sorted(s, 90), "p99": _percentile_sorted(s, 99),
            "max": s[-1] if s else math.nan}
summariseMedian of 9 (alternating)Runs (ms)
original: one sort per percentile308.7 ms309, 301, 309, 303, 322, 311, 319, 305, 308
sort once140.9 ms146, 135, 141, 141, 143, 135, 142, 134, 138

Source: snippets/RESULTS.md in _simeng_build

  • Speed-up of summarise: 2.19x; outputs identical: True. End to end (simulate + summarise): 1.20 s to 1.03 s (1.16x).
  • Amdahl's law: summarise got 2.2× faster, the whole run 1.16×, because the simulation itself was untouched (InfSim 08, slide 14).
  • Where it would matter more: in the Rust port, sorting is 45% of the instructions, so the same one-line change would be worth more there than in Python. The change is demonstrated here in a separate script rather than applied to the two simulators; doing so is a recorded follow-up (each repository's speed numbers would then need regenerating).

Benchmarks Are Distributions

The same command, run 40 times on an unchanged machine, takes 40 different times:

BenchmarkRunsMedianMeanMinMaxCVMAD95% CI of the median (bootstrap)
disagg-rs, whole process (wall clock)4060.3 ms59.1 ms52.4 ms64.1 ms5.6%1.3 ms59.3 ms to 60.9 ms
memsim, in-process repeats 2 to 4039891.1 ms893.5 ms866.5 ms966.5 ms2.2%7.4 ms885.6 ms to 896.7 ms

Source: snippets/RESULTS.md in _simeng_build

  • The distribution has two clusters, around 53 ms and 61 ms, not one bell. Frequency scaling, which core and hardware thread the process lands on, and the desktop all move it. A mean and a standard deviation describe this badly; the median and the MAD (median absolute deviation) describe it well.
  • Report an interval: a bootstrap confidence interval for the median (resample the runs with replacement, take the median, repeat 5,000 times) needs no assumption about the distribution's shape.
  • Warm-up depends on the runtime. memsim's first in-process run was no slower than the rest (0.99×): CPython 3.12 has no JIT to warm up. JIT-compiled runtimes, and anything with cold caches or lazy loading, need warm-up runs that are discarded (as criterion does by default; warm-up and replications).

Interactive: Designing a Regression Gate

A speed gate compares the median of k runs of the new build with the median of k runs of the baseline, and fails if the new one is slower by more than a margin. 12

Regression Detection in CI

  • Calibrate with an A/A test. Run the gate on unchanged code until you know its false-alarm rate. Here a single run against a single run with a 5% margin fails unchanged code 23% of the time.
  • Choose k and the margin together. The margin must sit well below the regression you want to catch: with a 10% margin, a 10% slow-down is caught only about half the time, whatever k is. Ten runs per side with a 5% margin gave 4% false alarms and caught 95% of 10% slow-downs.
  • Separate exact checks from timed ones. Behaviour (outputs, cycle counts, FLOPs) is gated exactly; time is gated statistically (deck 07). Instruction counts from cachegrind are a third option: deterministic and noise-free, though not the same thing as time.
  • Control the machine when you can: a dedicated runner, a fixed CPU frequency, no other jobs. One heavy job at a time also keeps a small machine from running out of memory, as it did more than once during this series.
  • Keep the raw samples as a build artefact, so a failure can be re-examined rather than re-run. criterion does this for Rust benchmarks and reports a confidence interval for each change (criterion user guide).
13

What to Take Away

  • USE for resources, profile first for code, and always check the answers after a change.
  • Read self and total time. Here the hot spot was in the metrics, not the engine: 45% of the Rust port's instructions were spent sorting.
  • Without perf, py-spy and cachegrind still work, unprivileged; cachegrind's instruction counts are deterministic.
  • Timings are distributions: report medians and intervals, and keep the raw samples.
  • Design gates from measured noise: an A/A test sets the false-alarm rate, and k and the margin set what is caught.
